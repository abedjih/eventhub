PHP CodeSniffer (PHPCS)

Vérification automatisée du respect des Drupal Coding Standards

PHPCS est l'outil de référence pour vérifier que votre code PHP respecte les Drupal Coding Standards. Il est inclus dans le package drupal/core-dev qui regroupe tous les outils de développement : PHPCS, PHPStan, PHPUnit, etc. Une seule commande pour tout installer.

bash
# Installation (inclut PHPCS, PHPStan, PHPUnit, etc.)
ddev composer require --dev drupal/core-dev:^11 -W

# Vérification
ddev exec vendor/bin/phpcs --standard=Drupal,DrupalPractice \
  --extensions=php,module,install web/modules/custom/

# Correction automatique
ddev exec vendor/bin/phpcbf --standard=Drupal web/modules/custom/

Le fichier phpcs.xml centralise la configuration pour que tous les développeurs et la CI utilisent les mêmes règles.

xml
<?xml version="1.0"?>
<ruleset name="Project">
  <rule ref="Drupal"/>
  <rule ref="DrupalPractice"/>

  <file>web/modules/custom</file>
  <file>web/themes/custom</file>

  <exclude-pattern>*/vendor/*</exclude-pattern>
  <exclude-pattern>*/web/core/*</exclude-pattern>
  <exclude-pattern>*/node_modules/*</exclude-pattern>
  <exclude-pattern>*/sites/*/files/*</exclude-pattern>

  <arg name="extensions" value="php,module,inc,install,test,profile,theme,css,info,txt,md,yml"/>
</ruleset>

Standards inclus

  • Drupal – conventions de base : nommage, indentation, docblocks
  • DrupalPractice – bonnes pratiques, APIs recommandées
  • Détection des APIs dépréciées

Intégration CI/CD

  • drupal/core-dev inclut : PHPCS, Coder, PHPStan, phpstan-drupal, PHPUnit
  • Ajouter dans la pipeline GitLab CI ou GitHub Actions
  • Bloquer les MR/PR non conformes

Ajoutez un hook pre-commit Git qui lance PHPCS et PHPStan automatiquement avant chaque commit. Fichier .git/hooks/pre-commit (chmod +x) :
bash
#!/bin/bash
# .git/hooks/pre-commit — PHPCS + PHPStan on staged files
FILES=$(git diff --cached --name-only --diff-filter=ACM \
  | grep -E '\.(php|module|install)$' \
  | grep -E '^web/(modules|themes)/custom')

if [ -z "$FILES" ]; then
    echo "✅ No custom PHP files to check"; exit 0
fi
echo "Files to analyse:"; echo "$FILES"; echo ""

# --- PHPCS ---
echo "🔍  PHPCS Verification..."
ddev exec vendor/bin/phpcs \
  --standard=Drupal,DrupalPractice \
  --extensions=php,module,install $FILES
if [ $? -ne 0 ]; then
    echo "❌ PHPCS found errors!"
    echo "Fix or use: git commit --no-verify"; exit 1
fi
echo "✅ PHPCS : OK"; echo ""

# --- PHPStan ---
echo "🔍 PHPStan verification..."
ddev exec vendor/bin/phpstan analyse $FILES --no-progress
if [ $? -ne 0 ]; then
    echo "❌ PHPStan found errors!"
    echo "Fix or use: git commit --no-verify"; exit 1
fi
echo "✅ PHPStan : OK"; exit 0

PHPStan – Analyse statique

Détecter les bugs sans exécuter le code

Contrairement à PHPCS qui vérifie le style, PHPStan vérifie la logique : types incompatibles, méthodes inexistantes, variables indéfinies. L'extension mglaman/phpstan-drupal (incluse dans drupal/core-dev) ajoute la compréhension des spécificités Drupal.

bash
# Déjà installé via drupal/core-dev (inclut phpstan + phpstan-drupal)
# Exécution
ddev exec vendor/bin/phpstan analyse web/modules/custom --level=6
yaml
# phpstan.neon
parameters:
    level: 6
    paths:
        - web/modules/custom
    tmpDir: var/phpstan

    # Ignored errors — structural incompatibilities with Drupal 11
    ignoreErrors:
        - identifier: missingType.iterableValue
        - { identifier: new.static, path: web/modules/custom/* }
        - '#Call to an undefined method Drupal\\Core\\Entity\\EntityStorageInterface::#'
        - '#Access to an undefined property Drupal\\Core\\Field\\FieldItemListInterface::#'
        - '#Cannot call method .+ on mixed#'
        - { identifier: globalDrupalDependencyInjection.useDependencyInjection,
            paths: [web/modules/custom/*.install, web/modules/custom/*.module] }
        - '#^Class .+ extends @internal class#'
        - identifier: method.alreadyNarrowedType
    reportUnmatchedIgnoredErrors: false

Niveaux d'analyse (0 à 9)

  • 0-1 : Erreurs basiques (classes manquantes)
  • 2-4 : Types de retour, appels incorrects
  • 5-6 : Analyse stricte des type-hints (recommandé)
  • 7-9 : Rigueur maximale, generics

ignoreErrors – Pourquoi ?

  • Drupal utilise des patterns (new static(), __get()) que PHPStan signale comme erreurs
  • Les ignoreErrors filtrent ces faux positifs structurels
  • tmpDir: var/phpstan → cache hors du dossier web
  • reportUnmatchedIgnoredErrors: false évite les warnings inutiles
⚠️
Ne pas démarrer au niveau 9 sur un legacy – progressez graduellement. Le niveau 6 est un bon équilibre pour Drupal 11.

Templates Twig & Preprocessors

Surcharger le rendu et enrichir les variables disponibles dans les templates

Drupal utilise Twig pour le rendu. Pour surcharger un template, il suffit de le copier depuis le module/core vers le dossier templates/ du thème en respectant la convention de nommage. Activez le debug Twig pour identifier les templates utilisés.

yaml
# sites/default/services.yml – activer le debug Twig
parameters:
  twig.config:
    debug: true        # affiche les suggestions de noms
    auto_reload: true  # recharge les templates modifiés
    cache: false       # désactive le cache Twig (dev only)
html (twig)
{# templates/content/node--event.html.twig #}
<article{{ attributes.addClass('event-card') }}>
  <h2>{{ label }}</h2>
  <div class="event-meta">
    <span class="event-date">{{ event_date }}</span>
    <span class="event-location">{{ location }}</span>
  </div>
  <div class="event-body">{{ content.body }}</div>
  {% if remaining_spots is not null %}
    <div class="event-spots">
      {{ remaining_spots }} place(s) restante(s)
    </div>
  {% endif %}
</article>

Les preprocessors dans .theme permettent d'ajouter ou transformer des variables avant le rendu Twig :

php
// eventhub_theme.theme
function eventhub_theme_preprocess_node(&$variables): void {
  $node = $variables['node'];
  if ($node->getType() !== 'event') {
    return;
  }
  // Ajouter des variables custom au template
  $variables['event_date'] = $node->get('event_date')->value;
  $variables['location'] = $node->get('location')->value;
  $variables['remaining_spots'] = \Drupal::service(
    EventManager::class)->getRemainingCapacity((int) $node->id());
}

function eventhub_theme_preprocess_page(&$variables): void {
  // Variable disponible dans page.html.twig
  $variables['site_name'] = \Drupal::config('system.site')
    ->get('name');
}

Conventions de nommage

  • node--event.html.twig → nœud de type event
  • node--42.html.twig → nœud spécifique
  • page--events.html.twig → page /events
  • field--field-name.html.twig → champ
  • Le debug Twig affiche toutes les suggestions

Preprocessors

  • THEME_preprocess_HOOK(&$vars)
  • Hooks : node, page, block, field, html
  • Ajouter des variables : $vars['ma_var']
  • Modifier les classes : $vars['attributes']
  • Accès aux entités et services

Bonnes pratiques Twig

  • {{ var }} → auto-échappé (anti-XSS)
  • {{ var|raw }} → JAMAIS sauf cas extrême
  • {% trans %}…{% endtrans %} → traduction
  • {{ attach_library('theme/lib') }} → CSS/JS
  • {{ dump(variable) }} → debug (dev only)

Routing Drupal 11

Déclarer les URLs, associer controllers/formulaires, protéger par permissions

Le fichier routing.yml mappe chaque URL à un controller ou formulaire. Les paramètres d'entité (ex: {event}) sont automatiquement convertis en objets par Drupal (param converter).

yaml
# eventhub_core.routing.yml
eventhub.event_list:
  path: '/events'
  defaults:
    _controller: '\Drupal\eventhub_core\Controller\EventController::list'
    _title: 'Événements'
  requirements:
    _permission: 'access content'

eventhub.event_view:
  path: '/event/{event}'
  defaults:
    _controller: '\Drupal\eventhub_core\Controller\EventController::view'
  requirements:
    _permission: 'access content'
  options:
    parameters:
      event:
        type: entity:event

eventhub.event_create:
  path: '/event/create'
  defaults:
    _form: '\Drupal\eventhub_core\Form\EventForm'
    _title: 'Créer un événement'
  requirements:
    _permission: 'create event'

eventhub.registration_cancel:
  path: '/registration/{registration}/cancel'
  defaults:
    _controller: '\Drupal\eventhub_registration\Controller\RegistrationController::cancel'
  requirements:
    _permission: 'register to event'
    _csrf_token: 'TRUE'

Clés de routing

  • _controller → méthode d'un Controller
  • _form → classe de formulaire
  • _permission → permission requise
  • _csrf_token → protection CSRF

Paramètres d'entité

  • {event} dans le path → objet Event injecté
  • Déclaration dans options.parameters
  • type: entity:event → param converter auto
  • 404 automatique si l'entité n'existe pas

Routes EventHub

  • 11 routes au total (CRUD + dashboard + API)
  • Protection par permission sur chaque route
  • CSRF sur les actions sensibles (cancel)
  • Route JSON pour l'autocomplétion geodata

Form API – Architecture

Le cycle de vie d'un formulaire Drupal : construction, validation, soumission

buildForm()→validateForm()→submitForm()

La Form API est le système central de Drupal pour les formulaires. Drupal gère le rendu HTML, la protection CSRF, et le cycle requête/réponse. Depuis Drupal 11, l'AutowireTrait simplifie l'injection de dépendances.

php
// RegistrationForm (module eventhub_registration)
class RegistrationForm extends FormBase {
  use AutowireTrait;

  public function __construct(
    private readonly EventManager $eventManager,
    private readonly RegistrationManager $regManager,
    private readonly EntityTypeManagerInterface $entityTypeManager,
  ) {}

  public function buildForm(array $form,
      FormStateInterface $form_state): array {
    $form['participant_name'] = [
      '#type' => 'textfield',
      '#title' => $this->t('Nom complet'),
      '#required' => TRUE,
      '#maxlength' => 255,
    ];
    $form['email'] = [
      '#type' => 'email',
      '#title' => $this->t('Email'),
      '#required' => TRUE,
    ];
    $form['add_phone'] = [
      '#type' => 'checkbox',
      '#title' => $this->t('Ajouter mon téléphone'),
    ];
    $form['phone'] = [
      '#type' => 'tel',
      '#title' => $this->t('Téléphone'),
      '#states' => [
        'visible' => [':input[name="add_phone"]'
          => ['checked' => TRUE]],
      ],
    ];
    return $form;
  }
}

Les 3 interfaces de formulaire

  • FormBase – formulaire standard
  • ConfigFormBase – config sauvegardée en YAML
  • ConfirmFormBase – confirmation avant action

AutowireTrait (Drupal 11)

  • Rend create() obsolète
  • Le constructeur suffit pour l'injection
  • Type-hints résolus automatiquement

#states (côté client)

  • visible / invisible selon un autre champ
  • required / optional dynamiquement
  • Entièrement JavaScript, pas de requête serveur

Formulaires AJAX

Mise à jour dynamique d'un formulaire sans rechargement de page

AJAX permet d'interroger le serveur pour recalculer un morceau du formulaire. Dans EventHub, la sélection d'une catégorie met à jour la capacité par défaut via le champ field_max_capacity du terme de taxonomie.

php
// EventForm – AJAX catégorie → capacité (EventHub)
$form['category'] = [
  '#type' => 'select',
  '#title' => $this->t('Catégorie'),
  '#options' => $categories,
  '#required' => TRUE,
  '#ajax' => [
    'callback' => '::updateCapacity',
    'wrapper' => 'capacity-wrapper',
    'event' => 'change',
  ],
];
$form['capacity'] = [
  '#type' => 'number',
  '#title' => $this->t('Capacité'),
  '#required' => TRUE, '#min' => 1,
  '#default_value' => $defaultCapacity,
  '#prefix' => '<div id="capacity-wrapper">',
  '#suffix' => '</div>',
];

public function updateCapacity(array &$form,
    FormStateInterface $form_state): array {
  return $form['capacity']; // retourne l'élément mis à jour
}

Mécanisme AJAX

  • 1. L'utilisateur change un champ (#ajax event)
  • 2. Drupal envoie une requête POST au serveur
  • 3. buildForm() est re-exécuté avec le nouveau form_state
  • 4. Le callback retourne l'élément à remplacer dans le DOM
  • Le #prefix/#suffix avec l'ID du wrapper est indispensable

Clés AJAX importantes

  • callback → '::methodName' (même classe)
  • wrapper → ID de la div à remplacer
  • event → événement JS (change, click…)
  • effect → animation (fade, slide)
💡
La valeur par défaut de capacity est recalculée dans buildForm() en lisant field_max_capacity du terme de taxonomie sélectionné. Le callback ne fait que retourner l'élément mis à jour.

ConfigFormBase – Formulaire de configuration

Stocker les paramètres du module en YAML, exportable et versionnable

ConfigFormBase crée un formulaire dont les valeurs sont stockées dans la Config API de Drupal (fichier YAML). Les valeurs sont exportables via drush cex et versionnables. Dans EventHub, EventHubSettingsForm (module eventhub_import) gère les paramètres d'import et de notification.

php
// eventhub_import/src/Form/EventHubSettingsForm.php
final class EventHubSettingsForm extends ConfigFormBase {

  protected function getEditableConfigNames(): array {
    return ['eventhub_import.settings'];
  }

  public function getFormId(): string {
    return 'eventhub_settings_form';
  }

  public function buildForm(array $form,
      FormStateInterface $form_state): array {
    $config = $this->config('eventhub_import.settings');

    $form['api_endpoint'] = [
      '#type' => 'url',
      '#title' => $this->t('Endpoint API géographique'),
      '#default_value' => $config->get('api_endpoint'),
      '#required' => TRUE,
    ];
    $form['import_batch_size'] = [
      '#type' => 'number',
      '#title' => $this->t("Taille de batch d'import"),
      '#default_value' => $config->get('import_batch_size'),
      '#min' => 10, '#max' => 500,
      '#required' => TRUE,
    ];
    $form['notification_email'] = [
      '#type' => 'email',
      '#title' => $this->t('Email de notification'),
      '#default_value' => $config->get('notification_email'),
      '#required' => TRUE,
    ];
    return parent::buildForm($form, $form_state);
  }

  public function submitForm(array &$form,
      FormStateInterface $form_state): void {
    $this->config('eventhub_import.settings')
      ->set('api_endpoint', $form_state->getValue('api_endpoint'))
      ->set('import_batch_size',
        (int) $form_state->getValue('import_batch_size'))
      ->set('notification_email',
        $form_state->getValue('notification_email'))
      ->save();
    parent::submitForm($form, $form_state);
  }
}

Les 3 méthodes clés

  • getEditableConfigNames() → liste des configs modifiables par ce formulaire
  • parent::buildForm() → ajoute le bouton « Save configuration » automatiquement
  • parent::submitForm() → affiche le message « The configuration options have been saved »

Config par défaut

  • Fichier config/install/eventhub_import.settings.yml
  • Valeurs initiales à l'activation du module
  • Exportable via drush cex, importable via drush cim
yaml
# config/install/eventhub_import.settings.yml
api_endpoint: 'https://geo.api.gouv.fr'
import_batch_size: 50
notification_email: 'admin@example.com'
💡
Pour les secrets (clés API, mots de passe), utilisez $settings dans settings.php plutôt que ConfigFormBase — les secrets ne doivent pas être versionnés dans les YAML.

Schema API & Database API

Créer des tables custom et interagir avec la base de données de manière sécurisée

La Schema API déclare la structure de tables dans le fichier .install. La Database API fournit une couche d'abstraction pour les requêtes SQL, avec protection automatique contre les injections.

php
// eventhub_core.install – table eventhub_geodata
function eventhub_core_schema(): array {
  $schema['eventhub_geodata'] = [
    'fields' => [
      'id' => ['type'=>'serial','unsigned'=>TRUE,'not null'=>TRUE],
      'code_commune' => ['type'=>'varchar','length'=>10,'not null'=>TRUE],
      'nom' => ['type'=>'varchar','length'=>255,'not null'=>TRUE],
      'population' => ['type'=>'int','unsigned'=>TRUE,'default'=>0],
      'departement' => ['type'=>'varchar','length'=>5,'not null'=>TRUE],
      'region' => ['type'=>'varchar','length'=>255,'default'=>''],
      'imported_at' => ['type'=>'int','not null'=>TRUE],
    ],
    'primary key' => ['id'],
    'unique keys' => ['code_commune' => ['code_commune']],
    'indexes' => ['nom' => ['nom'], 'departement' => ['departement']],
  ];
  return $schema;
}

// GeoDataRepository – SELECT avec LIKE
public function findByName(string $search, int $limit = 10): array {
  return $this->database->select('eventhub_geodata', 'g')
    ->fields('g', ['code_commune', 'nom', 'departement'])
    ->condition('nom', '%' . $this->database
      ->escapeLike($search) . '%', 'LIKE')
    ->range(0, $limit)->execute()->fetchAll();
}

// UPSERT – insert ou update par code_commune
public function upsert(array $data): void {
  $this->database->merge('eventhub_geodata')
    ->key('code_commune', $data['code_commune'])
    ->fields($data + ['imported_at' => time()])
    ->execute();
}

  • int, float – numériques
  • varchar(length) – texte court
  • text – texte long
  • blob – données binaires

Database API

  • Requêtes préparées = anti SQLi

  • Transactions pour cohérence des données

Database API – Requêtes CRUD

Insert, Select, Update, Delete : l'abstraction Drupal pour les tables custom

Toutes les requêtes passent par le service database (Drupal\Core\Database\Connection). Chaque méthode retourne un query builder chaînable terminé par ->execute().

php
// INSERT – ajouter un enregistrement
$id = $this->database->insert('eventhub_geodata')
  ->fields([
    'code_commune' => $data['code_commune'],
    'nom' => $data['nom'],
    'population' => $data['population'] ?? 0,
    'departement' => $data['departement'],
    'region' => $data['region'] ?? '',
    'imported_at' => $this->time->getRequestTime(),
  ])
  ->execute(); // retourne l'ID inséré
php
// SELECT – construire une requête de lecture
$query = $this->database->select('eventhub_geodata', 'g')
  ->fields('g', ['id', 'code_commune', 'nom', 'departement'])
  ->condition('departement', '75')
  ->orderBy('nom', 'ASC')
  ->range(0, 10);   // LIMIT 10 OFFSET 0
$results = $query->execute();
php
// UPDATE – modifier des enregistrements
$this->database->update('eventhub_geodata')
  ->fields([
    'nom' => $data['nom'],
    'population' => $data['population'] ?? 0,
    'imported_at' => $this->time->getRequestTime(),
  ])
  ->condition('id', $existing)
  ->execute(); // retourne le nombre de lignes modifiées
php
// DELETE – supprimer des enregistrements
$this->database->delete('eventhub_geodata')
  ->condition('departement', '00')
  ->execute(); // retourne le nombre de lignes supprimées

// TRUNCATE – vider toute la table
$this->database->truncate('eventhub_geodata')->execute();

Structure des requêtes

  • insert(table) → ->fields([])
  • select(table, alias) → ->fields(), ->condition(), ->orderBy(), ->range()
  • update(table) → ->fields([]), ->condition()
  • delete(table) → ->condition()
  • Toujours terminer par ->execute()

Méthodes Fetch

  • fetchAll() – tableau d'objets stdClass (toutes les lignes)
  • fetchAssoc() – tableau associatif de la prochaine ligne (['col' => val])
  • fetchField() – valeur scalaire du premier champ de la prochaine ligne
  • fetchCol() – tableau des valeurs d'une seule colonne
  • fetchAllAssoc(key) – tableau indexé par une colonne clé

Content Entity – Déclaration

Attribut PHP 8 #[ContentEntityType], classe de base, traits et handlers

Une Content Entity est le modèle de données principal de Drupal : stockée en base de données, elle est déclarée via un attribut PHP 8 sur la classe. L'attribut définit l'identifiant, la table, les clés et les handlers.

php
// src/Entity/Event.php
use Drupal\Core\Entity\Attribute\ContentEntityType;
use Drupal\Core\Entity\ContentEntityBase;
use Drupal\Core\Entity\EntityChangedInterface;
use Drupal\Core\Entity\EntityChangedTrait;
use Drupal\Core\StringTranslation\TranslatableMarkup;
use Drupal\user\EntityOwnerInterface;
use Drupal\user\EntityOwnerTrait;

#[ContentEntityType(
  id: 'event',                              // Identifiant machine unique
  label: new TranslatableMarkup('Event'),   // Label affiché
  label_collection: new TranslatableMarkup('Events'),
  label_singular: new TranslatableMarkup('event'),
  label_plural: new TranslatableMarkup('events'),
  base_table: 'eventhub_event',            // Nom de la table en BDD
  entity_keys: [                            // Colonnes spéciales
    'id' => 'id',                          // Clé primaire
    'uuid' => 'uuid',                      // Identifiant universel
    'label' => 'name',                     // Champ utilisé comme label
    'owner' => 'uid',                      // Propriétaire (user)
    'published' => 'status',               // Statut publication
  ],
  handlers: [                               // Services associés
    'access' => 'Drupal\eventhub_core\Access\EventAccessControlHandler',
    'views_data' => 'Drupal\views\EntityViewsData',
  ],
)]
class Event extends ContentEntityBase
    implements EntityChangedInterface, EntityOwnerInterface {
  use EntityChangedTrait;   // Gère automatiquement le champ 'changed'
  use EntityOwnerTrait;     // Gère automatiquement le champ 'uid'
}

Éléments obligatoires

  • id – identifiant machine unique
  • label – label traduisible
  • base_table – nom de la table SQL
  • entity_keys – mapping des colonnes clés (id, uuid, label)
  • Étendre ContentEntityBase
  • Implémenter baseFieldDefinitions()

Handlers courants

  • access – contrôle d'accès (view, update, delete)
  • form – formulaires (default, edit, delete)
  • list_builder – page de listing admin
  • views_data – intégration Views
  • storage – couche de persistance
  • route_provider – routes CRUD auto

Traits utiles

  • EntityOwnerTrait – champ uid + méthodes getOwner(), getOwnerId()
  • EntityChangedTrait – champ changed auto-mis à jour
  • RevisionLogEntityTrait – support des révisions
  • EntityPublishedTrait – champ status + isPublished()
💡
Drupal crée automatiquement la table en BDD à partir des base fields. Pas besoin de hook_schema() pour les entités.

Content Entity – Base Fields

baseFieldDefinitions() : déclarer les champs et leur configuration

Chaque champ est créé via BaseFieldDefinition::create(type). Les méthodes chaînées définissent label, contraintes, widget de formulaire et formateur d'affichage.

php
public static function baseFieldDefinitions(
    EntityTypeInterface $entity_type): array {
  // Récupère id, uuid, langcode du parent
  $fields = parent::baseFieldDefinitions($entity_type);
  // Ajoute uid (propriétaire) via le trait
  $fields += static::ownerBaseFieldDefinitions($entity_type);

  // STRING – texte court (varchar)
  $fields['name'] = BaseFieldDefinition::create('string')
    ->setLabel(new TranslatableMarkup('Titre'))
    ->setDescription(new TranslatableMarkup("Le titre de l'événement."))
    ->setRequired(TRUE)
    ->setSetting('max_length', 255)
    ->setDisplayOptions('form', [
      'type' => 'string_textfield', 'weight' => 0,
    ]);

  // TEXT_LONG – texte riche (table dédiée)
  $fields['description'] = BaseFieldDefinition::create('text_long')
    ->setLabel(new TranslatableMarkup('Description'))
    ->setDisplayOptions('form', [
      'type' => 'text_textarea', 'weight' => 5,
    ]);

  // DATETIME – date et heure
  $fields['event_date'] = BaseFieldDefinition::create('datetime')
    ->setLabel(new TranslatableMarkup("Date de l'événement"))
    ->setRequired(TRUE)
    ->setSetting('datetime_type', 'datetime')
    ->setDisplayOptions('form', [
      'type' => 'datetime_default', 'weight' => 10,
    ]);

  // INTEGER – nombre entier
  $fields['capacity'] = BaseFieldDefinition::create('integer')
    ->setLabel(new TranslatableMarkup('Capacité'))
    ->setRequired(TRUE)
    ->setSetting('min', 1)
    ->setDefaultValue(50)
    ->setDisplayOptions('form', [
      'type' => 'number', 'weight' => 20,
    ]);

  // ENTITY_REFERENCE – relation vers une autre entité
  $fields['category'] = BaseFieldDefinition::create('entity_reference')
    ->setLabel(new TranslatableMarkup('Catégorie'))
    ->setRequired(TRUE)
    ->setSetting('target_type', 'taxonomy_term')
    ->setSetting('handler', 'default:taxonomy_term')
    ->setSetting('handler_settings', [
      'target_bundles' => ['event_categories' => 'event_categories'],
      'sort' => ['field' => 'name', 'direction' => 'asc'],
      'auto_create' => FALSE,
    ])
    ->setDisplayOptions('form', [
      'type' => 'options_select', 'weight' => 25,
    ]);

  // LIST_STRING – liste de valeurs prédéfinies
  $fields['registration_status'] = BaseFieldDefinition::create('list_string')
    ->setLabel(new TranslatableMarkup('Statut'))
    ->setRequired(TRUE)->setDefaultValue('confirmed')
    ->setSetting('allowed_values', [
      'confirmed' => 'Confirmée',
      'pending' => 'En attente',
      'cancelled' => 'Annulée',
    ]);

  // BOOLEAN, CREATED, CHANGED – champs système
  $fields['status'] = BaseFieldDefinition::create('boolean')
    ->setLabel(new TranslatableMarkup('Publié'))
    ->setDefaultValue(TRUE);
  $fields['created'] = BaseFieldDefinition::create('created')
    ->setLabel(new TranslatableMarkup('Créé le'));
  $fields['changed'] = BaseFieldDefinition::create('changed')
    ->setLabel(new TranslatableMarkup('Modifié le'));

  return $fields;
}

Types de champs courants

  • string – varchar (max_length)
  • text_long – texte long avec format
  • integer / float / decimal
  • boolean – 0 ou 1
  • datetime – date / datetime
  • email – adresse email
  • entity_reference – relation
  • list_string – liste de choix
  • created / changed – timestamps auto
  • uri, link, image …

Méthodes de configuration

  • setLabel() – libellé affiché
  • setDescription() – aide contextuelle
  • setRequired(TRUE) – champ obligatoire
  • setDefaultValue() – valeur par défaut
  • setSetting(key, val) – réglage spécifique au type
  • setDisplayOptions('form', [...]) – widget formulaire
  • setDisplayOptions('view', [...]) – formateur d'affichage
  • setDisplayConfigurable('form', TRUE) – configurable via Field UI
  • addConstraint() – validation custom
💡
parent::baseFieldDefinitions() fournit id, uuid et langcode. Les traits ajoutent leurs propres champs : ownerBaseFieldDefinitions() pour uid.

Ajoutez des méthodes getters typées sur l'entité pour un accès propre aux données. Le Access Control Handler protège les opérations CRUD selon les permissions.

public function getCategory(): ?TermInterface {

// src/Access/EventAccessControlHandler.php
class EventAccessControlHandler extends EntityAccessControlHandler {

  protected function checkAccess(EntityInterface $entity,
      $operation, AccountInterface $account): AccessResultInterface {
    return match ($operation) {
      'view' => AccessResult::allowedIfHasPermission(
          $account, 'access content'),
      'update' => $this->checkUpdateAccess($entity, $account),
      'delete' => AccessResult::allowedIfHasPermission(
          $account, 'delete any event'),
      default => AccessResult::neutral(),
    };
  }

  protected function checkCreateAccess(AccountInterface $account,
      array $context, $entity_bundle = NULL): AccessResultInterface {
    return AccessResult::allowedIfHasPermission(
        $account, 'create event');
  }
}

Accéder aux valeurs

  • $entity->get('field')->value – valeur scalaire
  • $entity->get('field')->target_id – ID référence
  • $entity->get('field')->entity – entité référencée (chargée)
  • $entity->set('field', $value) – modifier
  • $entity->save() – persister
  • $entity->delete() – supprimer

Access Control Handler

  • Déclaré dans handlers['access']
  • Étend EntityAccessControlHandler
  • checkAccess() – view, update, delete
  • checkCreateAccess() – création
  • Retourne AccessResult::allowed(), forbidden(), neutral()
  • cachePerPermissions(), cachePerUser() – cache granulaire

Opérations CRUD sur l'entité

  • Event::create([...])->save()
  • Event::load($id)
  • Event::loadMultiple([$id1, $id2])
  • $entity->set('name', 'New')->save()
  • $entity->delete()

Base Fields vs Field UI

  • Base fields – définis en PHP, identiques pour toutes les instances, versionnés dans le code
  • Field UI fields – ajoutés via l'admin, stockés en config YAML, exportables avec drush cex
  • setDisplayConfigurable('form', TRUE) – rend le widget ajustable dans Field UI

Bundles (types)

  • Un bundle = une variante d'entité avec ses propres champs
  • Exemples Drupal core : Node → Article, Page, …
  • Défini par une Config Entity (bundle_entity_type)
  • Colonne type dans entity_keys
  • Chaque bundle peut avoir des champs Field UI différents

Config Entity (résumé)

  • Stockée en YAML (pas en BDD)
  • Attribut #[ConfigEntityType]
  • Étend ConfigEntityBase
  • Exportable / importable avec drush cex / drush cim
  • Utilisée pour : types de contenu, vocabulaires, vues, formats d'image…

Entity Query & Services métier

Requêter les entités et encapsuler la logique métier dans des services

L'Entity Query API est la méthode recommandée pour chercher des entités. Elle intègre automatiquement le contrôle d'accès et fonctionne avec tous les types d'entités.

php
// EventManager – événements à venir publiés
public function getUpcomingEvents(int $limit = 10): array {
  $ids = $this->entityTypeManager
    ->getStorage('event')->getQuery()
    ->accessCheck(TRUE)
    ->condition('status', 1)
    ->condition('event_date', date('Y-m-d\TH:i:s'), '>=')
    ->sort('event_date', 'ASC')
    ->range(0, $limit)->execute();
  return $this->entityTypeManager
    ->getStorage('event')->loadMultiple($ids);
}

Les services métier encapsulent la logique dans des classes réutilisables, injectables dans controllers, forms et hooks.

php
// EventManager – capacité restante
public function getRemainingCapacity(int $eventId): int {
  $event = $this->entityTypeManager
    ->getStorage('event')->load($eventId);
  if (!$event) return 0;
  $count = $this->registrationManager
    ->getRegistrationCount($eventId);
  return max(0, (int) $event->get('capacity')->value - $count);
}

// RegistrationManager – inscriptions non annulées
public function getRegistrationCount(int $eventId): int {
  return (int) $this->entityTypeManager
    ->getStorage('registration')->getQuery()
    ->accessCheck(FALSE)
    ->condition('event', $eventId)
    ->condition('registration_status', 'cancelled', '<>')
    ->count()->execute();
}

Entity Query – Avantages

  • Abstraction complète de la BDD
  • accessCheck(TRUE) obligatoire depuis D10
  • Conditions : =, <>, IN, BETWEEN, LIKE
  • exists() / notExists()
  • count()->execute() pour le comptage

Bons patterns de services

  • Un service = une responsabilité
  • Injection via constructeur + autowire
  • Méthodes typées (return types)
  • Réutilisable dans forms, hooks, controllers

Cache custom : stocker & lire

Injecter CacheBackendInterface pour enregistrer et récupérer des données calculées

Quand une requête est coûteuse (ex : charger les 5 derniers events), on peut stocker le résultat dans un cache bin et le relire sans requêter la base. On injecte le service cache.data via le constructeur.

php
use Drupal\Core\Cache\CacheBackendInterface;

class EventCacheService {

  public function __construct(
    private readonly CacheBackendInterface $cache,
    private readonly EntityTypeManagerInterface $entityTypeManager,
  ) {}

  /**
   * Retourne les 5 derniers events (depuis le cache ou la DB).
   */
  public function getLatestEvents(): array {
    $cached = $this->cache->get('eventhub:latest_events');
    if ($cached) {
      return $cached->data;  // Cache HIT → pas de requête DB
    }
    // Cache MISS → charger depuis la base
    $ids = $this->entityTypeManager->getStorage('event')
      ->getQuery()->accessCheck(FALSE)
      ->condition('status', 1)
      ->sort('created', 'DESC')
      ->range(0, 5)->execute();
    $events = $this->entityTypeManager
      ->getStorage('event')->loadMultiple($ids);

    // Stocker en cache (permanent, invalidé par tag)
    $this->cache->set(
      'eventhub:latest_events',              // CID (clé unique)
      $events,                               // données sérialisables
      CacheBackendInterface::CACHE_PERMANENT, // durée
      ['event_list'],                        // cache tags
    );
    return $events;
  }
}

BigPipe & Lazy Builders

Envoyer la page depuis le cache et injecter le contenu dynamique en streaming

Certains fragments changent à chaque requête (max-age: 0). Sans isolation, ils empêchent le cache de toute la page. Solution : un lazy builder remplace le fragment par un placeholder, et BigPipe l'injecte en streaming après l'envoi de la page.

// UpcomingEventsBlock – bloc avec lazy builder
#[Block(id: 'eventhub_upcoming_events',

    private readonly EventManager $eventManager,

  public static function create(ContainerInterface $container,
      array $configuration, $plugin_id, $plugin_definition): static {
    return new static($configuration, $plugin_id, $plugin_definition,
      $container->get(EventManager::class));
  }

  public function build(): array {
    // Lazy builder : le contenu sera injecté APRÈS l'envoi de la page
    return [
      '#lazy_builder' => [
        UpcomingEventsBuilder::class . ':build', [],

// UpcomingEventsBuilder – service TrustedCallbackInterface
class UpcomingEventsBuilder implements TrustedCallbackInterface {

  use StringTranslationTrait;

  public function __construct(
    private readonly EventManager $eventManager,
  ) {}

  public function build(): array {
    $events = $this->eventManager->getUpcomingEvents(5);
    $items = [];
    foreach ($events as $event) {
      $items[] = [
        '#type' => 'link',
        '#title' => $event->label() . ' – '
          . $event->getEventDate(),
        '#url' => Url::fromRoute('entity.event.canonical',
          ['event' => $event->id()]),
      ];
    }
    return [
      '#theme' => 'item_list',
      '#items' => $items,
      '#empty' => $this->t('Aucun événement à venir.'),
      '#cache' => ['max-age' => 0],  // jamais caché, mais ISOLÉ
    ];
  }

  public static function trustedCallbacks(): array {
    return ['build'];
  }
}

Fonctionnement BigPipe

  • 1. Drupal rend la page avec un placeholder HTML
  • 2. La page (cachée) est envoyée au navigateur
  • 3. BigPipe injecte le contenu dynamique en streaming
  • 4. Le navigateur affiche le résultat sans rechargement

BigPipe

  • Module activé par défaut (big_pipe)
  • Page envoyée avec placeholder
  • Contenu dynamique injecté via chunked transfer
  • L'utilisateur voit la page immédiatement

Lazy Builder : règles

  • TrustedCallbackInterface : interface de sécurité obligatoire. La méthode trustedCallbacks() déclare les callbacks autorisés dans le render array. Sans elle, Drupal refuse l'exécution
  • Les arguments doivent être des scalaires (int, string, bool) : Drupal sérialise les arguments dans le placeholder HTML pour les reconstruire après l'envoi de la page. Un objet ou un tableau ne peut pas être intégré dans un attribut HTML → passer un ID et recharger l'entité dans le builder
  • Le service doit être déclaré dans .services.yml
💡
Un lazy builder avec max-age: 0 ne contamine PAS la page grâce au placeholder. Sans lazy builder, un seul max-age: 0 rend toute la page non cacheable.

Queue Workers & Cron

Traiter des tâches lourdes de manière asynchrone

Les Queue Workers permettent de différer le traitement d'opérations longues. Le principe : un processus alimente la queue (createItem), le cron consomme les items (processItem).

php
#[QueueWorker(
  id: 'eventhub_geodata_import',
  title: new TranslatableMarkup('EventHub Geodata Import'),
  cron: ['time' => 60],
)]
class GeoDataImportWorker extends QueueWorkerBase
    implements ContainerFactoryPluginInterface {
  public function processItem(mixed $data): void {
    if (empty($data['code'])) return;
    $url = sprintf(GeoApiConstants::COMMUNES_ENDPOINT, $data['code']);
    $response = $this->httpClient->request('GET',
      GeoApiConstants::API_BASE . $url,
      ['query' => ['fields' => GeoApiConstants::COMMUNES_FIELDS]]);
    $communes = json_decode($response->getBody(), TRUE);
    $this->geoRepo->insertBatch(array_filter($communes,
      fn($c) => !empty($c['code']) && !empty($c['nom'])));
  }
}
php
// CronHooks.php – alimenter la queue par département
#[Hook('cron')]
public function cron(): void {
  $queue = $this->queueFactory->get(GeoApiConstants::QUEUE_NAME);
  if ($queue->numberOfItems() > 0) return; // skip si déjà en cours
  $response = $this->httpClient->request('GET',
    GeoApiConstants::API_BASE . GeoApiConstants::DEPARTMENTS_ENDPOINT);
  $depts = json_decode($response->getBody(), TRUE);
  foreach ($depts as $dept) {
    $queue->createItem(['code' => $dept['code'], 'nom' => $dept['nom']]);
  }
}

Cycle de vie

  • 1. Le cron appelle createItem()
  • 2. Le cron Drupal lance les workers
  • 3. processItem() traite un item
  • 4. Exception → item remis en queue
  • 5. cron.time = temps max par run

  • Injecter GuzzleHttp\ClientInterface

Permissions custom, protection CSRF, XSS et injections SQL

Drupal intègre des protections robustes, mais elles ne fonctionnent que si vous utilisez les bonnes APIs. Voici les 4 piliers de sécurité à maîtriser.

yaml
# eventhub_core.permissions.yml – permissions custom
create event:
  title: 'Créer un événement'
edit own event:
  title: 'Modifier ses propres événements'
edit any event:
  title: 'Modifier tout événement'
delete any event:
  title: 'Supprimer tout événement'
  restrict access: true    # visible uniquement par les admins
administer eventhub:
  title: 'Administrer EventHub'
  restrict access: true
yaml
# Sécuriser les routes avec _permission et _csrf_token
eventhub.registration_create:
  path: '/event/{event}/register'
  requirements:
    _permission: 'register to event'

eventhub.registration_cancel:
  path: '/registration/{registration}/cancel'
  requirements:
    _permission: 'register to event'
    _csrf_token: 'TRUE'       # token CSRF obligatoire
php
// Générer un lien avec token CSRF (pour les routes non-form)
use Drupal\Core\Url;
$url = Url::fromRoute('eventhub.registration_cancel',
  ['registration' => $id]);
// Le token est ajouté automatiquement par Drupal
// quand _csrf_token: 'TRUE' est dans le routing

// Protection SQLi – Database API = requêtes préparées
$this->database->select('eventhub_registration', 'r')
  ->fields('r')
  ->condition('event_id', $eventId)  // paramètre bindé, jamais concaténé
  ->execute();

Permissions custom

  • Déclarées dans module.permissions.yml
  • Utilisées dans les routes : _permission: 'nom'
  • restrict access: true → visible uniquement sur la page permissions des rôles admin
  • Vérifier en code : $account->hasPermission('create event')

Protection CSRF

  • Form API : token CSRF automatique sur tous les formulaires Drupal (champ caché form_token)
  • Routes non-form (liens d'action) : ajouter _csrf_token: 'TRUE' dans le routing
  • Url::fromRoute() détecte _csrf_token et ajoute automatiquement ?token=abc123 à l'URL
  • Le token est un hash HMAC basé sur le chemin de la route + la session de l'utilisateur
  • À chaque requête, Drupal recalcule le hash et le compare au token reçu
  • Token invalide ou absent → 403 Access Denied
  • Protège contre les attaques où un site tiers tenterait de forcer un clic utilisateur sur une action sensible (suppression, changement de statut…)

Protection XSS

  • Twig auto-escape : {{ variable }} échappe automatiquement
  • t() avec placeholders : @name (échappé), :url (filtré URL)
  • Xss::filter() pour du HTML contrôlé
  • JAMAIS |raw dans Twig sauf données de confiance

Protection SQLi

  • Database API : requêtes préparées (paramètres bindés)
  • Entity Query : entièrement sécurisé
  • JAMAIS de concaténation dans les requêtes SQL
  • accessCheck(TRUE) dans les Entity Query pour respecter les permissions

Config Split & Config Ignore

Gestion de la configuration par environnement

Config Split sépare la configuration par environnement. Config Ignore exclut certaines configs de l'import.

php
// settings.php
$config['config_split.config_split.dev']['status'] = TRUE;
$config['config_split.config_split.prod']['status'] = FALSE;

Config Split

  • Dev : devel, kint, verbose errors
  • Prod : cache agressif, syslog
  • Activation via settings.php

Config Ignore

  • system.site – nom/slogan par env
  • eventhub_import.settings – clé API
  • system.mail – transport mail
